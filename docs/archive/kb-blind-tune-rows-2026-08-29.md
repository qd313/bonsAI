# Fifty-one blind rows for the tune split, 2026-08-29

Same method as the two holdout batches — read
[kb-blind-holdout-rows-2026-08-28.md](kb-blind-holdout-rows-2026-08-28.md) first; this file records
only what is different and why the batch exists. Plain language on purpose.

## 1. Why blind rows in *tune* of all places

Blind rows exist to be a ship gate, and the two earlier batches went entirely to `holdout` for
exactly that reason — 56 rows, none in tune. Then the first measurement against them
([D37](maintainer-decisions-locked.md#d37--locked-endorsed-2026-08-29--blind-holdout-rows-added-to-kb_eval_v2-endorse-them))
turned up something the split boundary itself makes hard to act on, raised as **D38**:

| Split | keyword | vector_only | rrf (ships) |
|---|---|---|---|
| tune (117) | 75.2 / 86.3 | 74.4 / 91.5 | **75.2 / 91.5** |
| holdout (92) | 51.1 / 70.7 | **64.1 / 83.7** | 56.5 / 79.3 |

*(top-1 / top-3)*

On holdout the vector half alone beats the shipping fusion by 7.6 points of top-1. On tune the
fusion is the best arm there is. So the fusion weights look wrong — and **the only split it is
legitimate to tune against says change nothing.** The weight lock
(`knowledge_base_service.py:60-68`, 2026-08-09) is explicit that they must not be tuned from a peek
at holdout, and that rule is right; the problem is that tune could not see the defect at all.

The reason is structural rather than bad luck. Every tune row was card-derived — written by someone
looking at the card, so it reuses the card's own wording, which is what a keyword arm needs. **Tune
had no question that a keyword search would struggle with, so no weight change could ever look good
on it.** These 51 rows are the missing kind.

## 2. What is different from the holdout batches

Only the split, and one consequence of it. The procedure is unchanged: a metadata-only listing
(`section_id`, `name`, `section_type`, game `canonical_title`) generated by a throwaway script over
`data/kb/*.json`; the `card` field never read; questions written from that listing plus ordinary
knowledge of each title; **the split fixed at `tune` as part of writing the row, before anything
could be scored**; no retrieval, embedding or eval run performed while writing. The same automated
check ran afterwards — no non-stopword title token appears as a whole word in its query, every
target names a real card, `withheld_card_terms` is `[]`, and no query duplicates another anywhere in
the fixture. All 51 passed with nothing rewritten.

The consequence worth stating: **a row in tune is not a ship gate and is not pretending to be one.**
These exist so tuning has something honest to tune against. Holdout is untouched — still 92 labelled
rows, still the gate.

**Two deliberate near-pairs**, included because the corpus has the cards and nothing tested them:
*Hunter* against *Playing as the Hunter*, and *Jockey* against *Playing as the Jockey*. The queries
separate only by whose side you are on ("how do I get a teammate free when something pounces them"
against "any tips for pouncing well when I'm on the infected team"). If retrieval cannot tell the
survivor card from the infected-player card, that is worth knowing.

## 3. What was skipped, and one honest disclosure

- **State of Emergency**, again, entirely — same reason both earlier batches gave.
- **`Hollow Bough`, `Los Santos`, `Starter Lot`, `Sandtraps`, `Kerenzikov`, `Sandevistan`** — each
  skipped in an earlier batch for a recorded reason (not guessable from the title; too generic; or
  the honest paraphrase collides with a sibling card), and skipped here for the same reason rather
  than being second-guessed now.
- **`Dreadnought Twins` — skipped because this session's author is no longer blind to it.** During
  the `PHASE4-CHIPS-01` device work on 2026-08-29 the panel's chat history was read to check the
  carousel, and it contained a finished reply about that card, built from the card. That is card
  content, seen. It does not affect its existing holdout row `V2-BLIND-H27`, which was written and
  committed (`ebd2361`) before the device session, but writing a *new* row for it now would not be
  blind and it is not being written. **Recorded rather than quietly avoided**, because the value of
  every row in this family rests on the author saying accurately what they did and did not see.

## 4. Spread

51 rows across 12 of the 13 titles. Kinds: mechanic 27, boss 6, enemy 6, item 6, area 5, quest 1 —
mechanic-heavy because that is what the cards with no tune row happened to be. Every one targets a
card that had **no** tune row of any kind before this change; 45 of them have a holdout blind row
already, deliberately worded from a different angle so the pair is not a near-duplicate across the
split boundary.

## 5. What this changes

- **Labelled tune grows 117 → 168**, of which **51 are blind** where there were none.
- **Every tune number on record is superseded (R4)**, the same caveat each earlier batch carried.
  The arms figures in the table in §1 are the last measurement on the old tune set and are not
  comparable to anything measured after this change.
- **Holdout is untouched** — 92 labelled rows, unchanged, still the gate.
- **No measurement was run while writing these**, deliberately, and the split was fixed first. The
  first run against the new tune set happens after this merges.

## 6. What it is for

D38 asks how the fusion-weight finding can be acted on without spending the holdout. This batch is
the groundwork for the answer that does not spend it: with keyword-hostile questions in tune, a
weight sweep on tune alone can finally show whether a different keyword/vector balance is better,
and holdout stays untouched until there is one candidate to confirm. Whether that is the route taken
is still the maintainer's call — **D38 is deferred, not answered, pending more data**, which is what
this batch and further corpus growth are for.
