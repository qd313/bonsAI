## Phase 1 — three fixes, all cause-known, no decisions needed

### 1.1 Session context counts the newest turn twice (★★) — do this FIRST, it blocks QA Batch B

- **Symptom:** after one completed Ask, the *Session context* panel header reads "(2 turns)" and
  the expanded list shows the same question twice. Always n+1.
- **Cause (already established, verify then fix):** the strip builds its rows as archived turns
  **plus** the live turn ([SessionContextStrip.tsx:66-75](../../src/components/SessionContextStrip.tsx#L66-L75)),
  and after a completed Ask the newest turn is in **both**: it is in `askThreadCollapsed`, and
  `liveTurn` is still populated because `transparencySnapshot` still holds that turn's snapshot
  ([MainTabChatTranscript.tsx:801-812](../../src/components/MainTabChatTranscript.tsx#L801-L812) —
  line numbers may have shifted slightly; search for where the strip's props are built). Nothing
  de-duplicates them.
- **Fix lean (from the roadmap entry, follow it):** drop the **live row** when its id or question
  already matches the newest archived turn — the live entry only exists to cover the window
  before archiving. **Do NOT fix by subtracting one from the header count**; the duplicate row is
  the visible half of the bug.
- **Tests:** a unit test on the strip's row-building that renders one archived turn + a live turn
  with the same id/question and asserts one row; and the inverse (genuinely different live turn →
  two rows, so mid-Ask behavior is preserved).
- **Why first:** [20-frozen-chip-qa-batches.md](20-frozen-chip-qa-batches.md) § 4.3 checks the
  panel says "three turns" after three questions; with this bug it says four, so Batch B cannot
  run honestly until this lands.
- **Device check:** ask one question (rig cookbook below), read the strip header text via
  `deck_readPage`. Expect "(1 turn)".

### 1.2 Tap to hide does nothing (★) — root-caused 2026-08-27, small

- **Symptom (maintainer report, reproduced by script on device):** after revealing a spoiler,
  pressing A on *"Spoiler — tap to hide"* does nothing with the controller. Touch works.
- **Cause (measured, do not re-derive):** the collapse control
  (`.bonsai-spoiler-collapse-target`,
  [MainTabBonsaiAiMarkdownChunk.tsx:227-235](../../src/components/MainTabBonsaiAiMarkdownChunk.tsx#L227-L235))
  is a healthy Focusable with `onActivate` and the A-only guard — but it **never takes the
  ring**. The D-pad walk parks on the *section stop* that contains it
  (`bonsai-answer-stop`), and that stop's `onActivate` is a deliberate no-op
  (`stopNavProps` in [buildAnswerBubbleElement.tsx](../../src/utils/buildAnswerBubbleElement.tsx))
  kept so A cannot early-reveal a wait chip (STREAM-03). The spoiler fence registry registers
  only **masked** reveal targets, so no diversion ever offers the collapse control.
- **Fix lean:** in `stopNavProps`, make the stop's `onActivate` delegate to a contained
  `.bonsai-spoiler-collapse-target` **only** (query within the stop element; activate its
  collapse — the cleanest way is to click/invoke the same `setOpen(false)` path, e.g. by
  dispatching a click on the inner button, or by lifting the collapse into a small registry like
  the fence's). Reveal targets and wait chips must stay excluded — STREAM-03 holds.
  **Constraint from the 2026-08-04 QA row:** D-pad **Down** over a revealed fence must NOT
  collapse it. Only A.
- **Tests:** extend `buildAnswerBubbleElement.test.tsx`'s press block — a stop containing a
  collapse target: `onActivate` collapses; a stop containing a masked reveal target or wait
  chip: `onActivate` still does nothing.
- **Device check (three calls, state is easy to recreate):** reveal a spoiler (cookbook), walk
  Down to the stop showing *tap to hide*, press A, then
  `deck_readPage` counting `.bonsai-spoiler-reveal-target` (expect 1) and
  `.bonsai-spoiler-collapse-target` (expect 0).

### 1.3 A reply breaks a line mid-sentence (★) — desk-only, no device needed

- **Symptom:** rendered reply shows `…go BOOM` / newline / `. The trick is…` — the period
  orphaned at the start of the next line. The backend trace proves the model wrote one unbroken
  sentence (`…go BOOM. The trick is…`), so **our display layer introduces the break**.
- **Where to look:** the answer-section splitter — `splitResponseIntoChunks.ts` (final replies)
  and/or `prepareStreamMarkdown` / `streamMarkdownPrepare.ts` (streaming) in `src/utils/`. An
  all-caps token immediately before a period ("BOOM.") is the suspected trigger for a
  sentence-boundary heuristic.
- **Method:** write the failing test FIRST — feed the literal text
  `they walk right into ya and go BOOM. The trick is to keep your distance` through the
  splitter(s) and assert no chunk boundary lands between `BOOM` and `.`. Then fix the heuristic.
  Try other shout-words (`KABOOM.`, `RUN.`) while you are there.
- **Scope guard:** chunk boundaries are D-pad stops (Phase B). Do not change how many stops a
  normal multi-paragraph reply produces — the existing tests in
  `splitResponseIntoChunks.test.ts` and `buildAnswerBubbleElement.test.tsx` pin that; keep them
  green.

## Rig cookbook — the working on-device recipe (2026-08-27, all verified this session)

Environment: Deck at the `.env` IP, DPS MCP tools (`deck_*`), ESP32 bridge for real presses.

1. **First act of any device session: one harmless bridge press** (`deck_pressButton` with
   `DOWN`). `deck_status` does not report bridge health; the press's refusal message is loud and
   the fix is physical (replug the board). Never fall back to synthetic presses — they prove
   nothing about the nav graph.
2. **Deploy with the repo script, not `deck_deploy`** (that tool targets a lowercased path and
   fails — DPS P2-5): `./scripts/build.ps1` on Windows, `./scripts/build.sh dev` elsewhere.
   It verifies files and restarts the loader. **After any deploy, the QAM must be reopened**
   (`deck_openPlugin`); plugin DOM does not exist until then, so never `deck_waitFor` plugin
   selectors while it is closed.
3. **Prove the build before believing a run:** `md5sum dist/index.js` locally vs
   `~/homebrew/plugins/bonsAI/dist/index.js` over SSH, and reload/restart so the running QAM
   actually loaded it. The 08-26 session lost a day to a walk against an unproven build.
4. **Type a question with the injector, quotes INSIDE the remote command** (multi-word text is
   silently truncated otherwise — the docstring shows the fixed form):
   ```
   ssh deck@<ip> 'python3 - --text "your question here"' < scripts/deck_send_ask.py
   ```
   Then `deck_walkTo` DOWN to `ask` with `exact:true` (plain "ask" also matches "Attach
   screenshot to Ask") and press A.
5. **Wait for the reply** with `deck_waitFor` on a boolean expression (fence/Helpful mounted),
   generous `waitMs` (generations run up to ~3 min). **A timed-out wait with a truthy `value` is
   a finding, not an error** — follow it with a direct `deck_readPage` before concluding
   anything; the `satisfied` flag was observed false twice with a truthy value.
6. **Walks and assertions:** `deck_runSequence` with `mustReachText`, named `runName` → evidence
   file in `runs/` (commit it). `deck_readFocus` for the ring — trust `gpfocus`, never
   `activeElement`. `deck_readPage` for DOM facts — read-only, never drive UI with it.
7. **Frozen test chips** are pinned on the QA Deck (four spoiler-bait questions). Chips take
   focus individually with their question text; a 60×57 empty focusable in the carousel row
   swallows A (open bug) — before pressing A on a chip, confirm the focused element's own text
   is the question, or just use the injector.
8. **Card-attachment QA reads the Desktop ask trace, never the panel** (roadmap standing rule).
9. **Screenshots:** `deck_captureScreenshot` is broken (DPS P2-4, missing scripts in dist).
   Fallback: `scripts/screenshot-deck.ps1`.
