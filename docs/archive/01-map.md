## 5. Files owning more than one concern

**`src/utils/settingsPayload.ts` (109 lines) — settings payload *and* response
text.** It builds the settings RPC payload but also owns
`formatAppliedTuningBannerText` (`:74`) and `buildResponseText` (`:97`), which
format assistant reply/banner text. Different reasons to change, one file, and
the filename advertises only the first.

**`src/utils/settingsAndResponse.ts` — now a 16-line pass-through barrel.** It
contains no logic, only `export *` from three modules (`:14-16`):
`data/bonsaiSettingsSchema` (242 lines), `data/bonsaiSettingsNormalizers`
(437 lines), `utils/settingsPayload` (109 lines).

> **This invalidates REFACTOR-PLAN.md Phase 3.2.** The plan says to "split
> `settingsAndResponse.ts`" on the strength of its 34-file churn and its *and*
> name. That split already happened — the churn data predates it. What survives
> is a barrel with **22 importers**, which the plan's own "Combine when …
> pass-through re-export barrels" rule marks for removal, not splitting. The
> real *and* problem has moved into `settingsPayload.ts`.
>
> `src/utils/settingsAndResponse.test.ts` is still 468 lines and imports through
> the barrel, so it spans all three modules at once.

**`src/index.tsx` (1960 lines)** — plugin root, tab wiring, scoped CSS,
settings-save orchestration, and 7 direct RPC call sites. Highest fan-out in the
graph (54 imports).

**`main.py` (3021 lines)** — 55 RPC entry points plus in-handler business logic.
Its own module header (`main.py:5`) states it "delegates heavy work to
py_modules services", and it does import 35 of them; whether logic *also* remains
inline is REFACTOR-PLAN Phase 3.3 and is **not** answered here.

**`src/utils/` (87 files)** — a type bucket, not a concern. Contains RPC
transport (`deckyCall.ts`), persistence (`strategyChecklistPersistence.ts`),
text formatting, and heuristics side by side.

## 6. What this changes for later phases

1. **Phase 3.2 needs rewriting** — the split it prescribes is done; the barrel it
   would split is a merge candidate. See §5.
2. **Dead-code removal is a bigger, better-evidenced item than the plan assumed**:
   5 orphaned Proton RPCs + `proton_experiment_journal_service`, 6 other uncalled
   RPCs, and 1 dead service module — all traceable to the 2026-07-30 cleanup
   removing UI without removing what fed it. Good Phase 5 postmortem material.
3. **The boundary is narrow and well-contained** (15 files), so RPC-adjacent
   refactors have a small blast radius. The plan's fear of a sprawling boundary
   is not borne out.
